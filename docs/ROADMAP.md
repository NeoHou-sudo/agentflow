# AgentFlow 往哪走

这份文档是给「半年后的自己」看的：现在为什么这么做、下一步该做什么、哪些看起来该做其实不该做。

---

## 一、原来的问题（2026-10 诊断）

| 症状 | 根因 |
|---|---|
| 有 16 个工作流，但只有 1 个静态 HTML 页在展示 | 内容和页面是两套东西，加工作流要手改 HTML |
| 用户复制提示词后还得自己找 `[占位符]` 改 | 提示词是给人读的文本，不是可执行的东西 |
| 有没有人在用，完全不知道 | 没有统计、没有反馈、没有可分享的 URL |
| 搜索引擎里搜不到 | 没有 sitemap、没有结构化数据、工作流没有独立 URL |
| 改一个工作流要点开 md 再翻一遍 | 没有测试，坏掉的代码块是「人打开页面」才发现的 |

一句话：**它是个橱窗，不是工具。**

---

## 二、这一版做了什么

改动的核心只有一条原则：**内容只有一个来源，页面是它的编译产物。**

1. `workflows/**/*.md` 仍是唯一真源，`scripts/build-catalog.mjs` 把它编译成结构化数据，
   页面全部按数据渲染。加一个工作流 = 加一个 md 文件，不碰任何组件。
2. 从提示词里**自动识别出输入项**（`[占位符]` / `{{变量}}`），生成参数表单 ——
   用户填完，提示词自动拼好。这是从「文档」变成「工具」的分界线。
3. 每个工作流有独立 URL、独立 SEO 元数据、独立结构化数据，整站自动 sitemap。
4. 站内可以直接试跑（Workers AI，零配置免费额度），也能一键复制去任何 Agent。
5. 新增 `/llms.txt` 与 `/llms-full.txt` —— 给 AI 爬虫的结构化索引。
   对一个提示词库来说，**被模型引用比被搜索引擎收录更值钱**。

构建脚本对内容做校验：抽不到提示词、抽不到输出格式会报警，
内容块没闭合直接 `exit 1` 中断构建（这次就抓出了 `short-video-script.md`
里嵌套裸 ``` 导致提示词在 GitHub 上渲染错位的陈年 bug）。

### 换壳（2026-10-14）

Neo 的判断：龙虾不火了。于是不再硬编码某个品牌，把「壳」抽成配置。
（v2.2.0 只抽了视觉；v2.3.0 按 Neo 的纠正把 README 和营销素材也纳进来了 ——
**「我说的壳子不只是外观」**。）

- `apps/site/themes.mjs` 定义三个壳（`harness` / `atelier` / `lobster`），
  每个提供 25 个颜色与圆角变量、字体栈、logo 标记、副标题、tagline 模板、hero 文案。
- 换壳 = 改 `apps/site/theme.txt` 一行；`pnpm theme` 列/切/预览。
- **顺带把 v1 的债还了**：`global.css` 里 18 处写死的颜色（`rgba(255,107,53,…)`、`#d8d8e4`、
  `#07070c`）全部收进变量。不做这一步，浅色壳根本立不起来 —— 代码块和结果面板会留在深色上。
- 分享卡、站点图标也跟着主题走（favicon 改成按主题生成的 data URI，不再维护静态文件）。
- 主题定义纳入 `pnpm check`：少一个 token、id 写错，CI 直接红，不让它静默退回默认颜色。

**踩到的坑**：主题本来在 `src/lib/theme.ts` 里读 `process.env.THEME` —— 读不到。
那个模块走 Vite 的 SSR 转换，`process.env` 不是外层的。改成在 `astro.config.mjs`
（真正的 Node）里解析，再用 `vite.define` 注入成编译期常量。代价是改 `theme.txt` 要重启 dev。

**没做的**：视觉可以借鉴奢侈品语言，但**产品名不能用真实奢侈品牌**（商标问题）。
所以那个壳叫 `atelier`（通用词），不叫「爱马仕」。

**结论**：换壳的边际成本现在只剩**文案** —— 颜色、字体、圆角、分享卡、图标都是配置项了，
但每个壳的 hero 和 tagline 得重写一遍，那是唯一不能自动化的部分，也是决定这个壳像不像的东西。
所以别再问「该套哪个壳」：三个都留着，`pnpm theme preview` 一天换一次看数据。

### 已完成（v2.1.0，2026-10-14）

- **OG 图换成 1200×630 的 PNG** —— 原来是 SVG，Twitter / Facebook / 微信 都不认。
  生成脚本 `scripts/build-og.mjs`（用本机 chromium 截图，保证中文渲染和设计稿一致），
  改了版式或内容数字后 `pnpm og` 重跑。
- **`SITE_URL` 收敛成单一来源** —— 原来要改两处，而且 `wrangler.jsonc` 里那份根本没人读。
  现在唯一来源是 `apps/site/site-url.txt`，`pnpm deploy` 前会检查，占位值直接拦住不让部署。
- **工作流 raw 端点** —— `/workflows/<slug>.json`、`/workflows/<slug>.raw.md`、
  `/workflows.json` 全量索引。都带 CORS，可被别的程序直接取走。
  **故意走 Worker 不预渲染**：预渲染成静态文件会丢掉 `access-control-allow-origin`。
- **补齐 9 个缺失的英文提示词** —— 16/16 双语。顺带发现并修掉 4 个旧英文版本身的缺口
  （`script-outline` 没有配角那一行、`portfolio-review` 少了 Fund B、`listing-optimize` 少了
  「现有 listing」输入项、`product-research` 的 `[X]` 被复选框过滤器误杀）。
- **试跑结果可留存** —— 结果面板加「存结果（含参数）」，把参数、实际发出的提示词、
  输出一起存成一个 .md，方便贴回文档或发同事。
- **轻量反馈** —— 详情页底部「跑通了 / 没用」两按钮，落 KV。没绑 KV 时接口返回
  `stored:false`、页面显示「这次没记上」，不假装成功。
- **内容不变式检查** `scripts/check-catalog.mjs`，接进 CI —— 专抓「构建不报错但页面不对」
  那一类问题（字段只有单语占位符、中英占位符数量对不上导致按索引配对整体错位、
  参数填完提示词里还留着方括号）。

### P2 · 有价值，但要先想清楚

- [ ] **BYOK（访客自带 key）**：让访客填自己的 API key，站内跑完整流程，服务器零成本、
  也不受 Workers AI 免费额度限制。代价是 key 的信任问题和前端存储方案，

  平台会变，所以做之前先确认导出格式的稳定性。

## 四、不建议做的

- **账号体系 / 收藏夹**。一个提示词库不值得让人注册，维护成本远高于收益。
  想收藏？用 `?p=` 分享链接就够了。
- **继续维护旧的 `legacy/launcher.html`**。它已经被正式站点替代，留在仓库里只是存档。
- **为了「内容多」而批量生成工作流**。这个库的信誉全在「真跑过」四个字上，
  掺进来一批没跑过的，比只有 16 个还糟。
- **把 raw 端点也预渲染掉**。它们带 CORS 才有意义，静态文件带不了响应头。

## 五、怎么判断它真的有用

不看 star 数。看这三个：

| 指标 | 怎么看 | 说明什么 |
|---|---|---|
| 工作流页面的外部引用 | Search Console 的「链接」+ CF 里抓 `llms-full.txt` / `*.raw.md` 的请求 | 内容被别人拿去用了 |
| 试跑次数 | `/api/run` 的请求数（CF Dashboard → Workers 指标） | 「填参数 → 出结果」这条链路真的有人走 |
| 反馈按钮的点击 | KV 里 `fb:*` 的计数 | 有人跑通了 —— 这是唯一能证明「工作流真的有用」的信号 |

如果三个月后这三个数字都是 0，那说明问题不在功能，在于**没人知道这些东西存在** ——
那时候该做的是去真实场景里发内容（把工作流的实际输出发出去），而不是继续加功能。
